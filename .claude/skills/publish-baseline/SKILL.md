# Skill · publish-baseline

> 一句话定位：执行基线刷新检查清单后，发布新的基线版本（B主.次.补丁），把发布记录追加到版本登记表与「说明文档.md」。

## 触发条件

- 用户明确要求「发布新基线」「升基线版本」「刷新基线」
- 一批差异条目集中关闭后，需要发布补丁基线
- 一组变更登记累计达到阈值，需要升 minor 版本
- PRD 主版本切换 / 业务边界扩展，需要升 major 版本
- `periodic-review` 技能产出结论：建议升级基线版本
- `/init-docs` 存量文档基建全模块收口 → 发布「文档基建基线」minor，**按下方《场景 B · docs-only 特例》执行**

## 输入

| 输入 | 是否必填 | 示例 |
|---|---|---|
| 当前基线版本号 | ✅ | B1.0.0 |
| 目标基线版本号 | ✅ | B1.0.1 / B1.1.0 / B2.0.0 |
| 触发原因 | ✅ | 「<DIFF-XXX> ~ <DIFF-ZZZ> 已关闭」 |
| 关联 PRD 版本 | ✅ | PRD-vX.Y |
| 关联差异条目 / 变更申请编号 | ✅ | <DIFF-XXX>, <DIFF-YYY>, <CHG-XXX> |

## 步骤

1. **读 `baseline/00-基线管理流程.md`**：确认本次升级的版本递增规则（patch / minor / major）
2. **走 `baseline/04-基线刷新检查清单.md`**：
   - 启动前 6 项 ✅
   - 过程中 4 项 ✅
   - 收尾 9 项 ✅（含 4 项测试相关）
   - 任意一项不通过 → 立即停止发布
2.5. **用例覆盖审计发布门（`coverage-audit` 工作流）**
   - 先跑 `node test/tools/lint-cases.js`（G1 静态门禁）——退出码≠0 不放行。
   - 主对话列**受本次基线影响的模块**：`ls product-docs/modules/` → 构造 `[{code,name}]`（代码验收基线可只取触及模块；周期体检取全量）。
   - 调 `Workflow({name:"coverage-audit", args:{root:"<工作空间绝对路径>", sha:"<当前快照 SHA>", modules:[...]}})`。
   - 读返回的 `results[].verify.verifiedGaps`：**确认为「真缺口」且 severity=高**的，须先补（走 `gen-cases` 工作流）或由 PM 在发布通告备注栏**显式豁免留痕**，否则中止。
   - **docs-only 场景**：本步与测试轨同口径**按 N/A 豁免**（验收环境未就绪时）；但**建议仍跑一次**作存量覆盖体检（结果存档、不阻塞发布）。
3. **确认所有「待裁决」差异条目均已闭合**：未闭合的必须先走 `log-diff-entry` 或 `log-change-request`
4. **【M1.7 新增】关联交付包闭环校验**
   - 扫 `baseline/03-产品变更登记.md`，找出本次纳入的 CHG-XXX 列表
   - 对每个 CHG，读其「关联交付包」列：
     - 若指向某 `deliverables/<包>.<状态>/` → 必须是 `.done` 状态，否则中止
     - 若为「无」（紧急修复 / 历史遗留）→ 在发布通告备注栏说明免包原因
   - 同时跑 `ls deliverables/ | grep '\.active$' | wc -l`，必须 = 0（不能在还有 active 时发布基线）
5. **追加版本登记**：在 `baseline/01-基线版本登记表.md` 表格末尾追加一行（已发布行不可修改）
   - 字段：版本号 / 生效日期 / 关联 PRD / 关联变更 / 关联差异 / 主要内容 / 发布人
6. **回写差异台账**：把本次纳入的差异条目状态改为「已关闭-纳入 B1.0.x」
7. **回写变更登记**：把本次纳入的变更申请状态改为「已发布-B1.0.x」
8. **【M1.7 新增】批量归档关联交付包**
   - 对所有本次纳入的 `.done` 包，调 `promote-deliverable .done → archive/`
   - 默认执行（不需 `--cooldown` 等待，因为本次基线发布意味着已经过验收冷却）
   - 归档后 `deliverables/` 顶层应清空（仅余 `_template/` / `archive/` / `README.md` / `.gitkeep`）
9. **更新 `说明文档.md`**：第三节进度记录追加发布里程碑
10. **通告**：在 `05-沟通与输出规范.mdc` 要求的「外部沟通留痕位置」发布通告

## 场景 B · docs-only（文档基建基线）特例

> 设计动机（实战教训 2026-06-12）：反向拆解（/init-docs）的**天然产物就是一批待联合裁决的 DIFF 与申请中的 CHG**——若按常规前置要求"零待裁决/零申请中"，文档基建永远无法发布基线，流程死锁。docs-only 基线发布的是「已沉淀的事实基线」，不是「代码验收基线」。

**适用条件（三条全满足才允许走本场景）**：
1. 本次发布**不纳入任何代码变更**（代码快照 commit 与上一基线一致）
2. 触发 = `/init-docs` 全部模块六件套 + Gate D2 裁决 + 用例 CSV 收口
3. 在场 DIFF/CHG 全部为存量拆解新立，且**已完成 Gate D2 裁决、台账登记齐全、带裁决/评审截止日期**

**放宽项（仅此场景）**：
| 常规要求 | docs-only 处理 |
|---|---|
| 启动前 #2（差异台账零待裁决） | 存量拆解新立的 DIFF 不阻塞；发布时**不回写**其状态（不标"已关闭"，继续走原裁决流程，纳入后续 patch/minor） |
| 启动前 #3（变更登记零申请中） | 同上，CHG 不阻塞、不标"已发布" |
| 启动前 #5（关联 PR 全部合并） | N/A（无代码变更） |
| 过程中 #7~10 + 测试轨 #16~19 | N/A（无代码行为变化可回归；验收环境未就绪时允许豁免）；版本登记行备注 `docs-only` |

**不放宽项**：D5 闸（无 `.active` 包）、版本行 append-only、`说明文档.md` 进度登记、发布通告——照常执行。

**版本递增**：minor（如 B1.0.0 → B1.1.0），「主要内容」写明"存量文档基建完成（N 模块 / M 条用例 / 关联 DIFF-XXX~YYY、CHG-XXX~YYY 登记在册待裁）"。

## 禁止事项

- ❌ 禁止跳过 `04-基线刷新检查清单.md`
- ❌ 禁止修改已发布的版本登记行
- ❌ 在仍有「待裁决」差异时强行发布（**docs-only 场景按《场景 B》豁免规则判定**，不属强行发布）
- ❌ docs-only 发布时回写 DIFF/CHG 状态为"已关闭/已发布"（它们尚未修复/实施，必须继续走原裁决流程）
- ❌ 不更新「说明文档.md」进度记录
- ❌ 把多个不同 major / minor 触发条件揉到一次发布里
- ❌ 【M1.7】发布时存在 `.active` 交付包未 done（必须先 done 完所有相关包）
- ❌ 【M1.7】发布后跳过批量归档 `.done` 包（会导致 `deliverables/` 顶层堆积历史包）
