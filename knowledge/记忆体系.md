# 工作空间记忆体系设计 v1.0（2026-06-12）

> 🧬 某历史项目实战提炼的通用方法论 · 随骨架自带；文中项目专属案例叙事以占位示例呈现，路径示例按各项目实际替换。

> 背景：框架审计发现两类记忆病——① CLAUDE.md + MEMORY.md 每轮固定加载体积过大且互相矛盾（旧约定与新决议在两份事实源里并存数日 · 实战教训(示例)）② MEMORY.md 索引塞全文，一次性项目状态变成永久固定开销。
> 调研基础：2026 年主流 agent 记忆系统（Mem0 / Zep+Graphiti / Letta / LangMem / Hindsight）对比 + Claude Code 官方记忆文档。
> 结论先行：**本工作空间不引入向量库/记忆服务**——规模（几十个包、几百条记录）远未到需要向量检索的量级，纯文件 + grep 检索就是当前最优解；要借鉴的是这些系统的**分层架构与生命周期纪律**，不是它们的存储引擎。

## 一、外部调研结论（为什么这样设计）

### 1.1 主流系统怎么分层

| 系统 | 分层模型 | 对本工作空间的启示 |
|---|---|---|
| **Letta（原 MemGPT）** | OS 式三层：main context（RAM）/ recall（近期对话）/ archival（外部长期） | "每轮必载的内容要像 RAM 一样珍贵"——CLAUDE.md 即 main context，必须最小化 |
| **Mem0** | 抽取式：从对话提炼事实，新事实与旧事实比对后选 ADD/UPDATE/DELETE/NOOP | **矛盾消解必须是写入时动作**——新决议落盘时必须同步处理旧约定（UPDATE/DELETE），不能两个版本并存 |
| **Zep/Graphiti** | 双时态知识图谱：事实带"何时为真"区间 | 约定要带生效日期与废止日期（本空间的 LOCKED reason 行已在做） |
| **LangMem** | 语义（事实）/ 情景（经历）/ 程序（怎么做）三类 | 与本空间 patterns（语义）/ runs.csv+说明文档（情景）/ skills（程序）天然对应 |
| **Hindsight** | 事实抽取 + observations（从累积事实合成高阶洞察） | 即本空间 retrospector → patterns 的"案例升模式"链路 |

### 1.2 业界共识的四条纪律（2026）

1. **短期/长期二分已过时**，按"形态/功能/动态"三轴设计；落到文件系统 = 按**加载时机**分层（每轮必载 / 按需加载 / 检索加载）。
2. **遗忘是功能不是缺陷**——没有遗忘策略的记忆系统会污染判断（本空间已有 pattern dormant 机制，patch-011）。
3. **矛盾消解 ≤ 0.02 是发布指标**——两份事实源矛盾双载是记忆系统最严重的故障模式。
4. **记忆是上下文不是强制配置**（Claude Code 官方原话）——要"必然生效"的约束走 hooks/deny/脚本闸，记忆层只放需要判断力的内容。

### 1.3 Claude Code 官方机制（文件型记忆的事实约束）

- CLAUDE.md 每会话全量载入，**官方建议 < 200 行**；超长降低遵循度。
- MEMORY.md（auto memory）只载**前 200 行 / 25KB**，官方设计就是"索引 + topic 文件"。
- `.claude/rules/*.md` 支持 `paths:` frontmatter 按路径条件加载（适合代码库；本空间以流程为主、适用面有限）。
- 子目录 CLAUDE.md 按需加载（读到该目录文件时才载入）。

## 二、本工作空间的三层记忆架构

```
┌─ L0 工作记忆（本次会话/本条流水线 · 用完即弃）─────────────────┐
│ 会话上下文 · pipeline-state.json（包内 · 步骤/Gate 状态）        │
│ product-docs/_drafts/<包>/ 中间产物 · 终端输出                   │
├─ L1 情景记忆（发生过什么 · append-only 账本 · 按需检索）────────┤
│ 说明文档.md § 三 进度记录（人读主账本）                          │
│ evals/runs.csv + loops.csv + escapes.csv（机读账本）             │
│ knowledge/cases.csv（案例索引）· deliverables/提交记录.md        │
│ memory/<topic>.md（项目状态快照 · 经 MEMORY.md 索引进入）        │
├─ L2 语义+程序记忆（沉淀出的规则与方法 · 少量每轮必载）──────────┤
│ 每轮必载：CLAUDE.md（铁律+指针 · 目标 ≤ 250 行）                 │
│          MEMORY.md（纯索引 · 目标 ≤ 60 行）                      │
│          .cursor/rules/*.mdc（双 harness 时）                    │
│ 按需加载：knowledge/patterns/Pxxx（语义全文 · 指针目标）          │
│          .claude/skills + commands + agents（程序记忆）           │
│          knowledge/methodology/（30 张方法论卡片）                │
└──────────────────────────────────────────────────────────────┘
```

**分层判据 = 加载时机**，不是内容主题：
- 每轮都需要 → L2 必载区（所以必须极小）
- 做某类任务才需要 → L2 按需区（patterns/skills，靠指针进入）
- 回溯"当时发生了什么"才需要 → L1（grep/query-knowledge 检索）
- 只在本条流水线内有效 → L0（不准写进任何持久文件）

## 三、记忆动态（形成/巩固/遗忘/检索 · 各自的责任人）

| 动态 | 机制 | 责任人/工具 |
|---|---|---|
| **形成** | retrospector 落 runs/cases/loops + auto memory 记 topic 文件 | pipeline-retrospector / 主对话 |
| **巩固** | 案例 ≥ 2 次复现 → 提炼进 patterns；patches-pending → 月更合并进 agent prompt | /optimize-prompts 月更 |
| **遗忘** | pattern 连续 5 包未复现 → dormant（月更检查）；MEMORY.md 已完结条目 → 「已归档」段一行结论 | /optimize-prompts + 本设计 § 四.3 |
| **检索** | query-knowledge skill（A1/A3/A6 必跑）+ grep 账本 | 各 agent |
| **矛盾消解** | 写入时纪律（§ 四.1）+ 漂移对账（§ 四.4） | 主对话 + 对账脚本 |

## 四、写入纪律（本设计的核心增量 · 防再次矛盾双载）

### 4.1 决议类记忆的"双写"铁律

PM 决议（改变工作方式的决定）落 memory 时，**必须同一会话内回填权威文件**（CLAUDE.md / 对应 command / skill / rules），做不到就在 memory 条目尾标 `⚠️待回填`。
> 教训(示例)：某历史项目一条"可双向 push"决议先进了 memory，CLAUDE.md 旧约定隔了数天才回填——这段窗口期里每轮对话同时加载两条相反指令。

### 4.2 索引与全文分离

MEMORY.md 只放一行索引（链接 + ≤2 行摘要）；任何超过 3 行的内容进 topic 文件。CLAUDE.md 关键约束节同理（"铁律+指针"惯例，对 LOCKED 段同样适用——长操作模板下沉到脚本，正文只留指针，例 `scripts/git-sync.sh` / `git-biz-push.sh`）。

### 4.3 状态归档

在飞包条目（OPT-XXX 进展）是**情景记忆冒充语义记忆**的高发区：包升 .done 后，MEMORY.md 对应条目移「已归档」段压成一行结论；细节本来就在 99-状态.md / runs.csv 里，不需要第二份。

### 4.4 漂移对账（建议托管 scheduled task · 待 PM 启用）

每日/每周自动跑：① `grep "⚠️待回填" memory/MEMORY.md`（未回填决议）② runs.csv 包数 vs deliverables/*.done 目录数 ③ `bash scripts/audit-doc-vs-code.sh`（约定 vs 代码漂移 · 可选，项目自配；骨架不带）。
