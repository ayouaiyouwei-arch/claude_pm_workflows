# P008 · 双交付路径模式（路径 A 主仓中转 / 路径 B 直接派活）

> 🔧 骨架自带通用方法论。**仅适用于"项目有多个独立仓库"的场景**（如 <主仓> + <子仓>，例：主仓 + agent 仓 / 主仓 + sdk 仓 / 主仓 + 部署仓）· 单仓项目不启用。

## 描述

当工作空间端接了**多个独立仓库**后（如 <主仓> + <子仓>） · 需求**可走两条交付路径**给研发干活：

### 路径 A · 主仓中转（推荐 · 严控质量）

```
PM 写需求
   ↓ /new-feature 全流水线（A1~A7 8 agent + 5~6 Gate）
   ↓ 生成 .draft 包（含 12 根文件 + AGENTS + demo + baseline + 用例 + G 门）
   ↓ generate-research-deliverable 镜像到 code/<主仓>/docs/acceptance/<日期>-<slug>/
   ↓ git push origin feature/business-submit-<日期>（business 分支 · 主仓）
   ↓ write-fix-prompt 生成派活提示词
   ↓ PM 把提示词复制粘贴给研发
   ↓ 研发喂给 Codex · Codex 读主仓 docs/acceptance/<日期>-<slug>/ 干活
   ↓ Codex 在主仓 OR 其他子仓实施 + push
   ↓ PM 拉 主仓 release 看到 OR cd 子仓 && git pull 看到实施 commit
   ↓ P006 6 步追认 → .done
```

**特点**：
- ✅ 完整 _drafts 流水线（8 agent 全过 · 14 项硬检查 · G 门 · A5 LOCKED 硬约束）
- ✅ PRD / 接口契约 / 用例 / 验收 / 视觉规范 全套文档
- ✅ 主仓 docs/acceptance/ 作为 Codex 物理隔离工作视野
- ⚠️ 流水线耗时长（≥ 1 小时）

**适用场景**：
- P0/P1 需要严控质量的需求
- 涉及多端 / 多模块 / 跨仓的复杂改造
- 需要视觉规范 / 用例覆盖 / G 门拦截
- 触动核心架构（必须走 CHG 登记）

### 路径 B · 直接派活（仅紧急修复）

```
PM 发现线上问题（如 <子仓侧线上故障> / 配置错）
   ↓ 直接打开 子仓（如 <子仓>）· 让 Codex 用 IDE 跑修复
   ↓ Codex 在 子仓 commit + push main
   ↓ 工作空间端事后：cd 子仓 && git pull · grep 实施 commit
   ↓ 反向补档：从 commit message 提取信息 → 创建简化 .done 包（仅 99 + 08）
   ↓ baseline 补 CHG · 提交记录 row · runs.csv / cases.csv（P006 6 步压缩到 1 步）
```

**特点**：
- ❌ **无 _drafts 流水线**（跳过 A1~A7 8 agent）
- ❌ **无 14 项硬检查 / G 门 / A5 硬约束**
- ❌ **无主仓 business 分支 push**（业务侧 commit 字段标 "(无)"）
- ❌ **无完整 PRD / 用例 / 视觉规范**（仅 commit message + 99 + 08）
- ✅ 极快（已发现 → 已开发 1 小时内闭环）
- ✅ 适合 P0 线上熔断 / 配置类小改

**适用场景**：
- P0 线上紧急修复（如 <子仓侧线上故障影响生产>）
- 配置类 < 10 行小改（如 yaml / env 参数调整）
- 验收成本极低（如重启服务就能验）
- **修复面完全在子仓**（不涉及主仓业务代码）

## 选择决策树

```
新需求 → 判断
  ├── 触动核心架构？ → 路径 A（必走 CHG）
  ├── 跨端 / 跨仓 / L2+ 修改级别？ → 路径 A
  ├── 需要视觉规范 / UI 重构？ → 路径 A
  ├── P0 线上熔断 + 配置类小改 + 仅子仓？ → 路径 B
  └── 其他 → 路径 A（默认严控质量）
```

## 反例（**禁止重犯**）

### ❌ 反例 1：路径 B 滥用

把业务类需求（涉及主仓业务前端 / 后端）误判为路径 B 直接派活：
- 失去 8 agent 流水线的 PRD 完整性 / 用例覆盖 / G 门拦截
- 失去主仓 business 分支 push 流程
- 失去 14 项硬检查
- 后续 P006 追认时缺乏文档 → 复盘困难

### ❌ 反例 2：路径 A 滥用

线上 P0 紧急修复（如 <子仓侧线上故障>）走完整 `/new-feature` 流水线（8 agent · 1 小时）：
- 用户等不起
- 修复完成时 bug 可能已经被绕过 / 被掩盖
- 流水线产出的 PRD / 用例对配置类小改是过度设计

### ❌ 反例 3：路径 B 后不补档

PM 在子仓直接派活 Codex 实施后 · 工作空间端 deliverables/ 完全没有这个包：
- baseline/03 缺失 CHG 登记
- runs.csv / cases.csv 没记录 · 周报漏审
- 历史复盘时找不到这次修复的来龙去脉

**对策**：每次 `git pull` 子仓后 · 主对话主动 grep 新 commits · 发现未补档的子仓 commit 立即反向补档。

## 给新项目的提示

### `/init-project` 时的检查清单

`/init-project` skill 必须问 PM：

```
"你的项目是单仓还是多仓？
A. 单仓（默认 · 不启用 P008）
B. 多仓（启用 P008 + 拉子仓只读快照）"
```

如果选 B：
- PM 提供主仓 git URL + 拉/推分支
- PM 提供 N 个子仓 git URL（仅 main 分支 · 只读 · 不推）
- 工作空间端：
  - `code/<主仓名>/` ← 主仓快照（拉 release · 推 business）
  - `<子仓快照目录>/<子仓1>/`, `<子仓快照目录>/<子仓2>/` ... ← 子仓快照（拉 main · 不推）
- 业务侧 push 仍统一推主仓 business 分支 docs/acceptance/<日期>-<slug>/

详见 `CLAUDE.md § 双仓拉取约定` 模板。

## 操作模板

### 路径 A 模板

见 `.claude/skills/new-feature/SKILL.md` 标准 8 步流程。

### 路径 B 反向补档模板

```bash
# 1. sync 子仓拿到最新
cd <子仓路径>
git pull --rebase
git log --oneline --since="<上次 sync 日期>" | head -10

# 2. 对每个未补档的 commit · 创建简化 .done 包
PKG="<日期>-<分类编号>-<短描述>"
mkdir -p "deliverables/${PKG}.done/attachments"

# 3. 写 99-状态.md（必含字段：当前状态/commit SHA/类型/修改面/级别/状态变更历史）
# 4. 写 08-修复历史.md（[DONE-1] 段 · 含研发 commit + 实施摘要）

# 5. baseline/03 变更登记追加 CHG-XXX-X（状态 = 已发布）

# 6. deliverables/提交记录.md 追加 row（业务侧 commit 字段标 "(无)"）

# 7. evals/runs.csv + knowledge/cases.csv 各追加 1 行（P006 第 6 步强制）
```

## 残余风险

- ⚠️ 路径 B 包**无 14 项硬检查** · 质量保证依赖研发 + Codex 自检 + PM 端到端验收
- ⚠️ 路径 B 包**无完整文档** · 历史复盘 / 跨端影响分析时信息少 · 仅依赖 commit message
- ⚠️ 路径 B 包**容易忘记反向补档** · 必须 PM 端定期跑 `cd 子仓 && git pull && git log --since=...` 主动发现新 commits
