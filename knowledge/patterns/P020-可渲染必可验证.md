# P020 · 可渲染必可验证

## 描述

凡是**画在 canvas / WebGL 上、或任何 DOM 与截图都无法可靠断言**的可视化输出（地图折线/脊线、站点、聚焦/缩放/拖拽、ECharts/canvas 图表、热力图、轨迹等），缺陷往往**不是需求没描述清楚，而是验收测不出来**——需求本身完整，失效的是"没人能断言它到底画没画出来"。

**因此防御重心放在「测试 + 验收」，不放在「拦截需求/方案设计」。** 在设计阶段加"渲染契约=不予验收""方案无效"的硬闸，是把验收责任错误前移成设计门槛 → 给每个地图需求平添设计摩擦，却没真正解决"测不了"。

> 分工铁律：**设计阶段负责"想清楚要什么"，测试/验收阶段负责"确认做对没有"。** 渲染缺陷属后者。

## 正确的着力点

1. **（核心）A6 详细描述 `[MAP]` 测试用例**：每个肉眼可见 overlay 产 `[MAP]` 用例，详细到可程序断言——存在性 + 数量 + 几何（端点/坐标）。交互类断言行为结果（getCenter/getZoom）。**严禁用 `[VR]` 截图替代**（canvas 截图随瓦片/时刻/DPR 漂移，"没画出来"照样可能"通过"）。
2. **（基建）完善验收流水线**：独立验收回归框架补"地图 overlay 断言能力"，纯黑盒打真实环境，靠真实 DOM 的 `data-*` 钩子断言（非截图、非 mock）。
3. **（前置条件，不是设计门槛）测试钩子缺失 = test-blocker**：canvas-only 且无 `data-*` 钩子 → 由 A6/验收阶段标"测试前置条件未满足"，作为测试可行性要求提研发——它是**测试侧前置条件**，不是 A1 设计阶段"不予验收"硬闸。
4. **（轻量）A1 只做信息输入**：地图/canvas 类需求仅轻量标注"含渲染元素 X/Y/Z + 数据来源"作 A6 测试设计输入，不设契约硬闸。
5. **（灰度）P013 地图固定动作 M1~M5 兜底**。

## 触发条件

需求触及地图 overlay（折线/站点/实体 marker/轨迹/热力图/聚焦/缩放拖拽）、canvas/WebGL/SVG 动态图表 → A6 + 验收框架必跑；A1 仅轻量标注。
