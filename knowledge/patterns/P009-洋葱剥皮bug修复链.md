# P009 · 洋葱剥皮 bug 修复链（修好第一层暴露下一层）

> 🔧 骨架自带通用方法论。**经典软件工程教训**：复杂系统的 bug 经常层层嵌套被掩盖 · 修好第一层才会暴露下一层。**修复完任何一个底层 bug 后必须预判下一层可能出现什么**。

## 描述

**洋葱剥皮 bug** = 多个 bug 在系统中层层嵌套 · 浅层 bug 把深层 bug "短路 short-circuit" 了 · 所以深层 bug 一直没暴露；当浅层 bug 修复后 · 深层 bug 才浮出水面 · 看似"新 bug"· 实际是被掩盖的老 bug。

## 通用规律

```
Layer 1（最外层）
   ↓ short-circuit / fast-fail 掉
Layer 2（被掩盖 · 不显症状）
   ↓ short-circuit / fast-fail 掉
Layer 3（被双重掩盖）
   ↓
... 可能还有更深层
```

**触发条件**：
1. Layer 1 bug 是"硬失败"（throw exception / 立即拒绝）· 不是"软失败"（降级 / fallback）
2. Layer 1 失败导致 Layer 2 的代码路径根本没机会执行
3. Layer 2 同理掩盖 Layer 3

## 反例（**禁止重犯**）

### ❌ 反例 1：修一层就庆功

```
"Layer 1 修好了 · 任务完成 · 升 .done"
→ 等用户报"还有问题" · 再来追第二层 bug
→ 反复打补丁 · 用户信任下降
```

**对策**：每修一层后**主动跑端到端验收**（不仅修复点 · 而是完整业务流程）· 提前发现下一层。

### ❌ 反例 2：把后续暴露的 bug 当"新 bug"

```
研发："这是新发现的 bug · 之前没暴露过"
PM 复盘："每次都是被掩盖的老 bug · 我们的端到端验收能力不足"
```

**对策**：每次修底层 bug 时 · commit message **明确写** "可能掩盖了什么 · 修好后应预期暴露什么"。

### ❌ 反例 3：跳层修

PM 不知道 Layer 2 / Layer 3 bug 存在 · 上线 Layer 1 单包 · 用户当晚反馈 Layer 2 → 紧急修 · 上线后又反馈 Layer 3 → 再紧急修。

**对策**：底层 bug 修复完成后 · **预留 24 小时观察期** · 跑完整端到端验收 + dev gray 灰度真用一段时间 · 发现潜在下一层后一起 release。

## 检测 / 预防方法论

### 方法 1：commit message 显式预判

```markdown
fix(xxx): <Layer 1 bug 修复>

修复：<具体改动>

⚠️ 已知 short-circuit 链路：
  - 本 bug 修复前 · <某硬失败> 短路了 <某下层路径> · 可能掩盖 <预期下层 bug>
  - 建议下一步：跑完整 <端到端业务流程> · 观察 <下层指标>
```

### 方法 2：端到端验收硬指标

每个 P0/P1 修复 .done 前必须：
- 跑完整业务流程（不是只测修复点）
- 测耗时 / 日志 / 错误率
- dev gray 灰度真用 24 小时

### 方法 3：分层错误码 / metrics

每一层有独立的 error code + Prometheus metric · 即使浅层"全 OK" · 也能看到深层是否有异常（虽然没触发硬失败）。

## 应用场景

- **多组件串联系统**：A → B → C → D（4+ 层）每层都可能有默认值陷阱
- **复用第三方 SDK**：每层都可能有默认值陷阱（如 timeout 默认 600s）
- **配置驱动业务**：env / yaml / frontmatter（修一个配置暴露另一个）
