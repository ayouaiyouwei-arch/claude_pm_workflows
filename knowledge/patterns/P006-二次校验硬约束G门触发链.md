# P006 · 二次校验硬约束 G 门触发链

> 🔧 骨架自带通用方法论。这是一条"施工期质量保护链"模式——本文件解释"为什么 8-agent 流水线设计了这套四级拦截"。

## 描述

8-agent 流水线对**技术承诺中的不确定性**有一套**四级拦截机制**——从二次校验的预言、到施工时的硬门、到契约漂移流程、到 PM 决策回路——保证"先实施 / 失败时静默 / 用户看到脏态"的传统路径被替换为"施工首步实证验证 / 不成立则登记 + 等 PM"。

这套机制不是某个 agent 单独的能力，而是**多个 agent prompt + 模板**协作产出的施工期质量保护链。

## 为什么需要这个？

传统流程：
```
PM 写需求 → 研发实施 → 测试期发现底层假设错 → 返工 → 上线延期
```

带 P006 机制：
```
PM 写需求 → A4 列质询点 → A5 LOCKED 硬约束 → 06 验收 G 门
→ 研发施工首步 grep 验证 → 不成立则登记 DRIFT 等 PM
→ PM 改契约或重构后端 → 研发拉新契约继续
                    ↑
              零返工 · 早期拦截
```

## 已采取的对策（流水线内置 · 四级硬约束）

| 层 | 落点 | 触发条件 | 作用 |
|---|---|---|---|
| **L1 A4 § 七质询点（预言）** | `.claude/agents/scope-reviewer.md` prompt | A4 触发 A5 时强制列质询清单 | A4 角色把"接下来 A5 应该质询哪些点"显式写出来 |
| **L2 A5 实施硬约束 LOCKED（封装）** | `.claude/agents/secondary-reviewer.md` prompt | A4 触发 A5 时 | A5 角色把每条质询变成 LOCKED 硬约束 + 失败 fallback 路径 |
| **L3 06 验收 G 门（拦截）** | `deliverables/_template/06-验收标准.md` § 〇 实施前置门 | 任何 .draft 含技术承诺 | 研发施工第一件事就要跑 G 门 |
| **L4 04 契约 § 六 DRIFT 流程（闭环）** | `deliverables/_template/04-接口契约.md` § 六 契约漂移处理 | G 门触发 | 研发登记 DRIFT · 不允许自适应实现 · 等 PM 决策 |

## 触发使用指南

### 对 A4 范围审核

任何触发 A5 的包，A4 必须在范围审核报告 § 七 "要 A5 重点质询的点"里**显式列质询清单**，重点包括：
- 接口承诺是否能在现有架构下兑现（如"事务回滚"在细粒度事务架构下能否成立）
- 跨系统副作用是否能 rollback（WebSocket / 消息队列 / 缓存 / 外部 API）
- 异步操作是否在事务内
- 复用第三方组件签名是否需要修改

### 对 A5 二次校验

输出三路径质询后，**必须**在 § 三 给出"N 个实施硬约束"清单，每条必含：
- 硬约束编号（实施硬约束 1 / 2 / 3 ...）
- 施工动作（如"施工首步先 grep ..."）
- 失败时的 fallback 路径（如"不成立则标 [CONTRACT-DRIFT]"）
- LOCKED 状态（不允许研发自适应跳过）

### 对 .draft 包（PM 打包时）

- `06-验收标准.md § 〇` 必须写 **G0/G1/G2 ... 实施前置门**（与 A5 硬约束清单一一对应）
- `04-接口契约.md § 六` 必须含**契约漂移三步处理法**（停 / 登记 / 等 PM）
- `08-修复历史.md` ID 规则段必须含 `[CONTRACT-DRIFT-N]` 类型

### 对研发施工（Codex / 人类）

- **施工第一步 = 跑 G 门**（不是写代码）
- G 门不通过 = 必须登记 DRIFT + 等 PM · 严禁自适应实现
- DRIFT 段写两条可选路径供 PM 选 · 不要替 PM 拍板

### 对 PM 决策

收到 DRIFT 后：
1. 工作空间端实证核实（grep 源码 · 不信研发一面之词 · 也不替研发做技术决策）
2. 决策路径 · 标 `[ANSWER-N]` 留痕
3. 路径 A（改契约）通常优于路径 B（重构后端）· 除非后端有明显设计缺陷
4. 改完 push 新契约 commit · 不必新起 .draft 包

## 残余风险

- A5 硬约束依赖 A5 prompt 质量。如果某次 A5 漏判风险，施工时仍会盲实施。**对策**：A5 prompt 内嵌"技术承诺常见雷区清单"。
- G 门只在 PM 端 .draft 包内有效。如研发不读 06 直接照 03-PRD 实施，G 门被绕过。**对策**：00-给Codex的导读.md 必须显式说"施工第一步看 06 § 〇 G 门"。
- DRIFT 登记后 PM 决策延迟会阻塞研发。**对策**：DRIFT-N SLA 设 ≤ 24 小时 PM 必须给路径决策。

## 升格 / 降格条件

- **升格为 LOCKED**：连续 3 次 G 门触发 + PM 决策 + 闭环（验证机制稳定）
- **降格为已规避**：流程被规范化为 CI 自动跑 G 门后
- **降格为已废弃**：8-agent 流水线被重构掉 A4/A5 角色

## 给新项目的提示

骨架自带本机制的全部四级落点（A4/A5 prompt + 04/06 模板）。`/init-project` 完成后**不需要额外配置**——任何走 `/new-feature` 全流水线的包都会自动应用：

1. 任何 `.draft` 包打包后，研发施工**第一步是看 06-验收标准.md § 〇 G 门清单**
2. G 门挂掉 = 在 08-修复历史 加 `[CONTRACT-DRIFT-N]` 段 + 等 PM 决策（**绝不自适应实现**）
3. PM 决策后 [ANSWER-N] 留痕 + 改契约 → 研发继续

⚠️ **A5 硬约束 prompt 内嵌的"技术承诺常见雷区清单"**（事务边界/异步副作用/复用签名/跨服务一致性/资源锁）应**按你项目实际技术栈本地化**。新项目接入时 review `secondary-reviewer.md` prompt 的实施硬约束段，按项目实际技术栈补充雷区。
